# 일일 메뉴 저장 방식 변천사

## Overview
[[menu-manager-page]]의 "일일 메뉴"(오늘의 메뉴 목록) 저장 방식이 두 차례 바뀌었다. **문서(매뉴얼)와 실제 코드 사이에 시점 차이가 있으므로, 최신 상태는 반드시 코드 기준으로 판단할 것.**

| 시점 | 방식 | 근거 |
|---|---|---|
| ~2026-08-10 이전 | 필드 단위 실시간 자동 저장 (저장 버튼 없음) | [[onban-admin-manual]] 3.4절: "예전의 '💾 일일 메뉴 저장' 버튼은 제거되었습니다" |
| **2026-08-20 ~ (현재)** | **명시적 "💾 일일 메뉴 저장" 버튼으로 회귀** (실시간 연동 폐지) | `menu-manager.html` 코드 주석: "실시간 연동 폐지, 2026-08-20" (2026-08-26 코드 직접 확인) |

즉 2026-08-10자 관리자 매뉴얼([[onban-admin-manual]])의 "실시간 저장" 서술은 **이후 폐지되어 현재는 다시 명시적 저장 버튼 방식이다.** 매뉴얼 갱신 필요.

## 현재(2026-08-20~) 동작 — 코드 기준
- 일일 메뉴(`menus`) 쪽 편집(추가·수정·삭제·재고±·사진)은 서버로 바로 안 보내고 로컬에만 반영 → `_menuDirty=true` → 상단 "💾 일일 메뉴 저장" 버튼을 눌러야 서버 반영
- 반면 **메뉴창고 마스터(`all`) 쪽은 여전히 즉시 저장** — 일일 메뉴와 마스터가 서로 다른 저장 정책을 쓴다 (코드: `function _save(ctx){if(ctx==='all')saveAllMenus();else{_menuDirty=true;...}}`)
- 저장 버튼을 누르면 `#savingOverlay`로 **화면 전체를 차단**(팝업 위까지 덮는 z-index 1500) — 저장 왕복 도중 다른 조작(개별삭제·재고±·날짜/페이지 이동 등)이 상태를 건드려 저장이 바뀐 상태를 그대로 덮어써버리는 문제(2026-08-22)를 막기 위함. "홈으로 가기"만 오버레이보다 z-index를 높여 예외로 둠
- 사진 편집 시 상태 메시지가 문맥에 따라 다름: 일일 메뉴 쪽은 "사진이 적용됐어요(\"일일 메뉴 저장\" 눌러야 반영)", 마스터 쪽은 "사진이 저장되었습니다!"(즉시)

## 왜 되돌아갔는가 (추정 근거: 코드 주석 + 관련 메모리)
실시간 자동 저장 기간 중 다음과 같은 문제가 있었던 것으로 보인다:
- 저장 왕복 도중 다른 동작이 상태를 덮어써버리는 경쟁 상태 (코드 주석 2026-08-22)
- 메뉴 저장 데드락 재발 이력 — 이 프로젝트에는 별도로 추적 중인 "메뉴 저장 데드락 재발 이력" 메모리가 있으며, 4차례 재발까지 있었음. 재발 시 락 범위부터 확인하라는 지침이 있음(이 vault 밖, Claude 메모리 기준)
- 일일 메뉴 저장이 매번 마스터 카탈로그 전체를 재동기화하던 성능 문제 (커밋 `b591206`)

## 다른 저장 개념과의 구분 (혼동 주의)
"저장"이라는 단어가 이 서비스 안에서 최소 3가지 다른 의미로 쓰인다:
1. **일일 메뉴 저장** (이 페이지의 주제) — 2026-08-20 이후 다시 명시적 버튼 + 전체 화면 차단 방식
2. **메뉴 창고 저장** ([[menu-warehouse]]) — 오늘 메뉴를 날짜별 이력으로 스냅샷 보관하는 별도 동작. 위 저장 방식 변천과는 무관
3. **설정 값 저장** — 예: 예약 이벤트는 "저장"/"비우기" 버튼, 발송 설정(SMS/알림톡)은 토글 즉시 반영(버튼 없음)이 항목마다 다름
4. **마스터 메뉴(메뉴창고 all) 편집** — 이쪽은 계속 즉시 저장 방식 유지 (일일 메뉴만 명시적 버튼으로 회귀했음에 주의)

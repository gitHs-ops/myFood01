1. 문서 개요

1.1 목적

본 문서는 온반(溫飯) "오늘의 반찬" 관리자 운영 페이지(menu-manager.html)의 내부 구조, 탭별 기능, 상태 관리, API 연동, 알림 발송 흐름을 상세히 기술한다. 유지보수·기능확장·장애대응의 기준 자료로 사용한다.

1.2 범위

구분대상설명
Admin Frontendmenu-manager.html관리자 단일 페이지 앱(SPA). 메뉴관리·카카오발송·주문관리·창고·설정 5탭
진입 허브index.html관리자 비밀번호 인증 후 세 페이지(관리자메뉴·고객메뉴·주문관리) 연결
Backendserver/server.jsExpress REST API. 관리자가 사용하는 모든 API 엔드포인트 제공
외부 서비스ImgBB API · GAS(알림 프록시)이미지 호스팅 / SMS·알림톡 발송 (서버 위임)

1.3 시스템 특징 요약

  • 단일 파일 SPA — Vanilla JS로 탭 전환(switchPage(name)). 외부 프레임워크 없음.
  • 이중 저장 모델 — 일일 메뉴·마스터 메뉴를 클라이언트 배열(menus[], allMenus[])에 즉시 반영하고, 저장 버튼 또는 변경 즉시 API를 통해 DB와 동기화.
  • 실시간 주문 수신 — SSE(/api/events) + 15초 폴링 이중 구조로 신규 주문을 놓치지 않음.
  • 알림 발송 서버 위임 — GAS URL·SMS·알림톡 호출이 server.js 내 _notifyOrder / _notifyStatus로 이전. 클라이언트는 API 응답만 수신.
  • 이미지 호스팅 — ImgBB 무료 API를 통해 메뉴 이미지를 외부에 업로드하고 URL만 DB에 저장.

2.1 탭 전환 메커니즘

// switchPage(name) — 모든 .page 요소를 비활성화 후 해당 탭만 .active 추가
function switchPage(name) {
  document.querySelectorAll('.page').forEach(p => p.classList.remove('active'));
  document.getElementById('page-' + name).classList.add('active');
  // 탭별 진입 훅: orders → renderOrders(), history → renderHistory(), 등
}

탭 전환 시 별도 HTTP 요청 없이 DOM 표시만 전환. 단, 주문관리(orders)·창고(history) 탭 진입 시 최신 데이터를 자동 조회한다.

4. 인증 및 접근 제어

4.1 비밀번호 인증 흐름

  1. 페이지 로드 시 즉시 실행 함수(IIFE)가 sessionStorage.getItem('onban_admin_auth') 확인
  2. 값이 '1'이면 인증 완료 — 페이지 정상 표시
  3. 없으면 prompt()로 비밀번호 입력 요청
  4. 일치 시 sessionStorage.setItem('onban_admin_auth','1') 저장 → 같은 탭·세션 재입력 불필요
  5. 불일치 시 location.replace('onban.html')로 즉시 고객 페이지 리다이렉트
(function(){
  var ADMIN_PW = 'onban@1dl34';          // 소스 내 평문 — 변경 시 이 위치만 수정
  if (sessionStorage.getItem('onban_admin_auth') === '1') return;
  var input = prompt('관리자 비밀번호를 입력하세요');
  if (input === ADMIN_PW) { sessionStorage.setItem('onban_admin_auth','1'); }
  else { alert('접근 권한이 없습니다.'); location.replace('onban.html'); }
})();

4.2 세션 범위

  • 브라우저 탭 종료 시 sessionStorage 초기화 → 다음 접속 시 재인증 필요
  • 같은 탭에서 새로고침 시 재인증 불필요
⚠ 클라이언트 측 평문 비밀번호 방식. 소스 보기(Ctrl+U)로 노출 가능. 운영 환경에서는 서버 세션 또는 JWT 인증으로 개선 권장.

5.5 💾 일일 메뉴 저장 (saveToday())

  1. POST /api/menu/daily 호출 (body: {date, menus[]})
  2. 서버: daily_menus 덮어쓰기 + menus(마스터) 자동 병합(UPSERT)
  3. SSE broadcast('menu_updated') → 고객 화면 자동 갱신
  4. 성공 시 _menuDirty = false. 플로팅 버튼 비활성화

save()는 _menuDirty=true 설정 후 동일하게 API를 즉시 호출한다. saveToday()와 save()는 같은 엔드포인트를 사용하며, 저장 버튼은 UI 확인 용도다.

📦 탭 3 — 주문 관리 (page-orders)

5.7 주문 목록 조회

탭 진입 시 renderOrders()가 자동 호출된다. GET /api/orders?date=workDate(작업일자 기준 주문)와 GET /api/orders?addreqDate=workDate(작업일자에 접수 완료된 예약주문 보완 조회)를 Promise.all로 병렬 조회 후, id 기준으로 병합해 _ordersCache에 저장한다. 예약주문은 접수 시 date가 예약일로 바뀌어 첫 번째 조회만으로는 당일 접수건이 누락되므로 두 번째 조회로 보완한다.

주문 통계 카드 (orderStats)

항목집계 기준
전체orders.length
대기중(pending)status === 'pending'
주문접수(confirmed)status === 'confirmed'
배송완료(delivered)status === 'delivered'
취소된주문(cancelled)status === 'cancelled'
예약주문status === '예약주문' 또는 (status === 'confirmed' 이면서 추가요청이 작업일자+"예약주문함"으로 시작)

주문 목록 필터 탭 (orderFilterTabs)

전체 / 대기중 / 주문접수 / 배송완료 / 취소된주문 / 예약주문 탭으로 필터링. 각 탭에 건수 배지 표시. 예약주문 탭은 통계 카드와 동일 조건(원본 예약주문 + 작업일자 접수완료건)으로 필터링되어, 접수 처리된 예약주문도 계속 이 탭에서 확인 가능하다.

예약 관련 주문의 상태 라벨은 목록·상세 팝업 모두에서 앞에 빨간 예약/ 접두어가 붙는다(예: "예약/주문접수").

추가 요청 뱃지 (addreqBadge)

주문 목록 중 additionalRequest가 있고 addreqAcked === false인 건수를 탭 상단 빨간 뱃지로 표시. 해당 주문 카드는 addreq-new 클래스로 붉은 테두리 + 맥박 애니메이션.

5.10-1 예약주문 판별·처리 규칙

고객이 예약주문 페이지에서 신청한 주문은 status:'예약주문', reserveDate(희망 배송일), additionalRequest가 "{신청일} 예약주문함"으로 시작하는 형태로 저장된다. 관리자 화면은 이 세 가지 신호를 조합해 예약 기원 여부를 판별한다.

판별 시점조건사용처
접수 전status === '예약주문'주문접수 버튼 → "✅ 예약 주문 접수"로 라벨 전환
접수 후(오늘 신청분)status==='confirmed' && additionalRequest가 작업일자+"예약주문함"으로 시작예약주문 필터·통계·상태 라벨(예약/주문접수)
접수 후(임의 시점)reserveDate 존재배송완료 버튼 활성 조건, 재주문 시 예약 승계

✅ 예약 주문 접수 처리 시 confirmOrder()가 PUT /api/orders/:id/status {status:'confirmed'}를 호출하며, 서버는 status==='confirmed' && prev==='예약주문' 조건에서 date 컬럼을 reserve_date 값으로 갱신한다.

⚠ 예약주문은 신청/접수/배송완료 전 과정에서 재고 차감·복원·검증 로직을 모두 우회한다(8.x 참고 — 상세설계서 8절 유사 규칙 적용).

8. 핵심 비즈니스 로직

8.1 일일 메뉴 추가 (addMenu())

  1. 카테고리·이름·가격 유효성 검사 (비어있으면 alert)
  2. 중복 체크: 동일 이름 메뉴가 menus[]에 이미 있으면 경고 표시 (추가는 허용)
  3. 새 메뉴 객체 생성. id는 Date.now(), menuId는 마스터 ID (없으면 null)
  4. menus[]에 push 후 save() 호출 → API POST /api/menu/daily
  5. _clearAddForm()으로 입력 폼 초기화
  6. renderAll()로 화면 갱신

8.2 신 메뉴 등록 (saveNewMasterMenu())

  1. 팝업 입력값(이름·카테고리·가격·재고·설명) 읽기
  2. POST /api/menu/master/merge {menus:[{name,cat,price,stock,child,desc}]} 호출
  3. 서버: menus 테이블 UPSERT (name+cat UNIQUE)
  4. 성공 시 allMenus[]에 추가 → 자동완성 목록 즉시 갱신
  5. 팝업 닫기. 자동완성에서 새 메뉴 선택 가능 상태

8.3 메뉴 전체 편집 저장 (saveMenuEditAll())

  1. 팝업(menuEditOverlay)에서 이름·가격·재고·카테고리·설명·이미지URL 읽기
  2. 대상 배열(imgCtx) 내 항목 갱신 + touch(m)(updatedAt 갱신)
  3. _save(editCtx) 호출: 'menus' → saveMenus / 'all' → saveAllMenus
  4. 마스터 변경 시 syncAllMenuToMenus()로 일일 메뉴에도 반영
  5. 팝업 닫기 + _render(editCtx)

8.4 중복 메뉴 병합 (doMerge(targetId, sourceId))

  1. confirm 확인
  2. POST /api/menu/master/delete {menuId: sourceId} 호출
  3. 서버: menus에서 sourceId 삭제 + daily_menus·orders에서 sourceId → targetId로 일괄 업데이트
  4. 클라이언트: allMenus에서 sourceId 항목 제거 + renderAllMenus

9. 이미지 업로드 (ImgBB)

9.1 이미지 팝업 구조

이미지 관련 컨텍스트는 imgCtx 변수('menus' | 'all')로 구분한다. 동일 팝업(imgOverlay)과 함수를 공유하며, 저장 시 _arr(imgCtx)와 _save(imgCtx)를 통해 해당 배열에 반영한다.

9.2 업로드 흐름

  1. 파일 선택 (onFileSelected(e)) — FileReader로 base64 변환
  2. uploadToImgBB(b64) — POST https://api.imgbb.com/1/upload?key=IMGBB_KEY
  3. 응답 data.url 추출 → pendingImgUrl에 저장
  4. 미리보기 갱신 (setImgPreview(url))
  5. [사진 저장] 버튼 활성화
  6. 저장 클릭 → saveImg() → 대상 메뉴 imgUrl에 URL 기록 → _save(imgCtx)

9.3 메뉴 편집 팝업 내 이미지

메뉴 편집 팝업(menuEditOverlay)에도 동일 ImgBB 업로드 로직이 존재한다. 사용하는 변수만 다르다 (editPendingImgUrl, editCtx). 팝업 저장(saveMenuEditAll()) 시 editPendingImgUrl이 imgUrl로 반영된다.

⚠ ImgBB 무료 플랜은 이미지가 영구 보존되지 않을 수 있음. 운영 중요도가 높은 이미지는 별도 스토리지(S3 등) 사용 권장.

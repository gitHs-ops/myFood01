1. 문서 개요

1.1 목적

본 문서는 온반(溫飯) "오늘의 반찬" 고객 주문 서비스의 고객용 프론트엔드와 이를 지원하는 백엔드 API의 내부 구조·데이터 흐름·비즈니스 로직을 상세히 기술하여, 유지보수·기능확장·장애대응의 기준 자료로 사용하는 것을 목적으로 한다.

1.2 범위

구분대상설명
Frontendonban01.html고객 주문 단일 페이지 앱(SPA). 메뉴 조회·장바구니·주문·결제안내·주문내역 전 기능
Backendserver/server.jsExpress 기반 REST API + SSE 서버. 메뉴/주문/고객/설정 데이터 관리

1.3 시스템 특징 요약

  • 무(無)로그인 주문 — 디바이스 식별자(device_id, UUID v4) 기반으로 주문자 정보를 자동 인식한다.
  • 단일 파일 SPA — 외부 프레임워크 없이 Vanilla JS로 페이지 전환(.page.active 토글) 방식으로 구현.
  • 실시간 동기화 — SSE(Server-Sent Events)로 주문 상태 변경을 즉시 반영.
  • 이중 저장 모델 — 주문 내역을 서버 DB(정본)와 localStorage(캐시·항목편집 작업본)에 동기 유지.
  • 동시성 안전 재고관리 — 트랜잭션 + SELECT ... FOR UPDATE로 동시 주문 품절을 방지.

4. 화면(페이지) 설계

4.1 페이지 전환 메커니즘

모든 페이지는 하나의 HTML 문서 안에 <div class="page"> 로 존재하며, goPage(name) 함수가 .active 클래스를 토글하여 표시 페이지를 전환한다(display:none ↔ block). 전환 시 해당 페이지의 렌더 함수를 호출하고 window.scrollTo(0,0) 한다.

page id화면진입 시 호출렌더 함수
page-list메뉴 목록초기 activerenderCatTabs(), renderMenuGrid()
page-cart장바구니goPage('cart')renderCart() (+ 선택항목 flush)
page-orderer주문자 정보cartOrder()renderOrdererPage()
page-order주문 확인goPage('order')renderOrder()

page-history주문 내역goPage('history')renderHistory()
⚠ 전환 가드: 주문내역에서 항목(수량·삭제)을 편집한 뒤 재주문 미처리 상태로 다른 페이지로 이동하면 goPage()가 confirm()으로 경고하고, 강행 시 _revertPendingItemEdits()로 원본을 복원한다 (목적지가 history/payment인 경우는 예외).

4.6 주문자 정보 페이지 (renderOrdererPage)

  • 진입 시 device_id로 /api/customers-master 조회 → 이름·전화·주소1 자동 채움(_cachedMaster 캐시).
  • 입력: 이름(필수)·전화(필수)·배송주소(픽업 외 필수)·배송방법(셀렉트)·추가요청(최대 200자).
  • 배송방법: 경비원실(기본)·문앞·택배함·현관직접수령·매장픽업.
  • 주소 목록 버튼(showAddrList) — 이름+전화 입력 시 활성화. 저장 주소(addr1~3) 선택/수정.
  • 확정 시 검증: 이름·전화 필수, 픽업 외 주소 필수, 2만원 미만은 매장픽업만 허용.

4.7 결제 안내 페이지 (renderPayment)

진입 시 /api/settings에서 은행 계좌 정보(banks, primary 우선)를 최신 조회하여 BANK 갱신 후 렌더. 계좌번호 복사(copyAccount → clipboard), 입금 안내 문구 표시. (시트 조회 실패 시 임시 기본값 국민은행/김현철/118210210117.)

4.8 주문 내역 페이지 (renderHistory → _doRenderHistory)

  • /api/orders?date=&deviceId=(오늘자)와 /api/orders?deviceId=&reservedForDevice=1(이 기기의 예약일자 보유 주문 전체)을 Promise.all로 병렬 조회해 id 기준 병합한 뒤 localStorage.orders와 동기화한다. 예약주문이 접수(confirmed)되면 서버가 date를 예약일자로 갱신해 첫 번째 조회만으로는 누락되므로, 두 번째 조회로 보완한다.
  • 서버 항목으로 status·memo·adminReply·additionalRequest·reserveDate·date를 갱신하되 items(수량)는 로컬 편집본 유지.
  • 오늘자 "phantom 주문"(DB에 없는 로컬 전용 항목) 제거 — 예약일자 보유 항목은 date가 오늘이 아니므로 이 제거 대상에서 자연히 제외됨.
  • 목록 표시 필터: o.date===menuDate || !!o.reserveDate — 오늘자 주문뿐 아니라 예약일자가 미래로 바뀐 접수완료 예약주문/예약이벤트도 함께 표시.
  • 상태 뱃지: pending(대기중)·confirmed(주문접수)·delivered(배송완료)·cancelled(취소됨). 예약주문은 별도 status 값을 쓰지 않고 일반 주문과 동일한 상태 흐름을 따르며, reserveDate(예약일자)가 존재하는지만으로 판별해 타임스탬프 뒤에 빨간색 "예약주문 (MM/DD)" 라벨을 추가로 표시.
  • 항목 클릭 → openOrderDetail(id) 상세 팝업(_buildOrderCard): 수량편집·삭제·배송방법수정·추가요청·재주문·취소.
  • 재주문 버튼(btn-reorder-)은 진입 시 스냅샷(_snap) 대비 실제 변경분이 없으면 기본 비활성화. 수량·항목·배송방법 변경 시에만 _updateReorderBtnState가 활성화하며, 값을 원복하면 다시 비활성화된다(추가요청 단독 수정은 활성화 대상 아님).

4.9 예약주문 페이지 (goPage('reserve'))

  • 마스터 메뉴 전체(/api/menu/all)를 카테고리 탭 + 페이지네이션(_reservePage)으로 조회, 카드 클릭으로 _reserveSel(Object, menuId→{qty 등})에 토글 선택.
  • 1개 이상 선택 시 하단 플로팅 바(#reserveSubmitBar)가 document.body에 직접 부착되어 뷰포트 기준으로 항상 노출된다(스크롤에 밀려 화면 밖으로 사라지는 것을 방지하기 위해 페이지 내부가 아닌 body 직속으로 렌더). 페이지 이탈 시 명시적으로 제거.
  • 예약 주문 신청하기 클릭 → openReservePopup(): 예약 날짜 입력 범위를 오늘+1일 ~ 오늘+7일로 제한(_reserveDateMin/Max). 팝업 타이틀은 "예약주문", 하단 버튼은 저장(submitReserveOrder) / 닫기(closeReservePopup) 2개로 구성.
  • 입력 필드 순서·자동채움·주소 목록 로직은 주문자 정보 페이지(4.6)와 동일 컴포넌트를 공유하며, _addrTarget('orderer' | 'reserve') 전역값으로 대상 폼을 구분한다.
  • 배달료 로직은 4.6과 동일(2만원 미만 매장픽업만, 이상 시 +1천원) — _updateReserveTotal()에서 실시간 계산 반영.
  • 신청(submitReserveOrder) 시 주문 객체: id:'RSV'+ts, status:'pending'(일반 주문과 동일), reserveDate, additionalRequest:요청사항 원문 그대로. 예약 여부는 오직 reserveDate 필드로만 판별하며, status나 추가요청 텍스트에 별도 표식을 넣지 않는다.

4.10 예약 이벤트 카드 (loadReserveEvent / _renderReserveEventCard)

  • 데이터 저장 위치: 별도 테이블 없이 settings k-v(/api/settings)의 reserveEvent 키에 {name, desc, price, deadline} JSON으로 저장(관리자 설정 화면에서 입력).
  • loadReserveEvent()가 window.onload와 loadReserveMenus() 양쪽에서 호출되어, 메뉴 목록 페이지·예약주문 페이지 어디서 진입해도 최신 이벤트 정보를 반영한다. deadline이 오늘보다 과거면 _reserveEventData=null로 카드가 숨겨진다.
  • 카드 마크업은 _renderReserveEventCard() 한 곳에서 생성해 #menuListEventCard(오늘의 메뉴 페이지)와 #reserveEventCard(예약주문 페이지) 두 컨테이너에 동일하게 주입한다(배지+설명+기한 한 줄 요약, 두 위치 스타일 통일).
  • 카드 클릭 → _selectReserveEvent(): _reserveSel['EVENT']에 {id:'EVENT', name, cat:'이벤트', price, qty:1}을 추가하고 즉시 openReservePopup() 호출. #reserveOverlay가 position:fixed 전역 오버레이라 페이지 이동 없이 어떤 화면에서 클릭하든 바로 예약 팝업이 뜬다.
  • 예약 날짜 범위 특례: openReservePopup()에서 _reserveSel['EVENT']가 있으면 _reserveDateMin=이벤트 deadline, _reserveDateMax=deadline+7일로 재계산한다(일반 예약주문의 "오늘+1~7일"과 다른 규칙). 날짜 입력 힌트(#reserveDateHint)와 유효성 오류 문구도 이벤트 여부에 따라 동적으로 바뀐다.

8. 핵심 비즈니스 로직

8.1 동시성 안전 재고 차감

POST /api/orders는 트랜잭션 내에서 각 항목을 SELECT stock ... FOR UPDATE로 잠근 뒤 재고를 확인하고 차감한다. 한 건이라도 부족하면 전체 롤백 후 soldOut 반환. menu_id 우선, 없으면 name 폴백.

BEGIN
  for item in items:
     SELECT stock FROM daily_menus WHERE date=? AND menu_id=? FOR UPDATE
     if stock < qty: soldOut.push(...)
  if soldOut: ROLLBACK; return {success:false, soldOut}
  for item in items:
     UPDATE daily_menus SET stock = stock - qty WHERE ...
  INSERT INTO orders (...)
COMMIT → broadcast('order_new')
⚠ 클라이언트도 주문 확정 직전 verifyStock()로 1차 확인하지만, 최종 정합성은 서버 트랜잭션이 보장한다(이중 방어). 클라이언트 검사 통과 후 서버에서 품절 시 _notifyOutOfStock()로 안내.

8.2 주문 취소 ↔ 재주문의 재고 정합성

전이재고 처리
active(pending/confirmed/delivered) → cancelled재고 복원 (stock + qty)
cancelled → active재고 재차감 (GREATEST(stock - qty, 0))

재주문(reorder)은 "기존 주문 취소 → 신규 주문 생성" 순서로 처리한다. 신규 주문이 재고부족으로 실패하면 localStorage에서 신규·원본을 제거하고 원본 상태를 서버에서 복원한 뒤 품절 모달을 띄운다. 편집 스냅샷(_snap)으로 취소된 원본은 최초 주문 내용으로 되돌린다.

8.3 배달료·최소주문 정책

  • 배달료는 품목 합계 ≥ 20천원(2만원)이고 매장픽업이 아닐 때만 +1천원.
  • 2만원 미만 주문은 매장픽업만 허용 — 주문 확정·재주문·내역 배송방법 변경 모든 지점에서 강제(_updateDeliveryFee, histMemoSelChange, _updateHistTotal).
  • 내역에서 항목 삭제로 2만원 미만이 되면 배송방법을 매장픽업으로 자동 전환 + 경고.

8.4 주문내역 항목 편집의 "미확정" 모델

주문내역에서 수량·삭제 편집은 즉시 DB에 반영하지 않고 _pendingItemEdits 플래그로 작업본만 변경한다. 편집 시작 시 _snapOrig()로 원본을 _snap에 스냅샷. 재주문 처리해야 확정되며, 미확정 상태로 이탈/닫기/새로고침하면 _revert* 함수가 원본으로 복원한다(물리 반영 방지).

8.5 메뉴 자동 갱신

_startMenuAutoRefresh()가 1초 인터벌로 카운트다운하여, 메뉴 목록이 활성이고 모달이 닫혀있고 탭이 보일 때 10초마다 loadMenus(true) 재조회. 사용자 활동(click/scroll/key/touch)이 있으면 카운트를 리셋(_markMenuActivity).

8.6 예약주문의 재고 예외 처리

예약주문은 배송 희망일이 미래이므로, 재고 검증 대상에서 완전히 제외된다. 예약주문 여부는 오직 reserve_date 컬럼이 NULL이 아닌지로만 판별하며, status 값이나 추가요청 텍스트는 판별에 전혀 관여하지 않는다(과거엔 status==='예약주문' / additionalRequest 텍스트 매칭도 병행했으나, 신호가 여러 개라 혼란을 유발해 reserve_date 단일 기준으로 정리함).

💡 reserve_date는 접수(confirmed) 이후에도, 심지어 배송완료·취소 이후에도 컬럼값이 유지되므로, 주문의 생애주기 전체에서 예약 기원 판별이 흔들리지 않는다.

8.7 예약주문의 재주문(reorder) 승계

예약주문 원본을 재주문하면, reorder()는 !!order.reserveDate만으로 예약 기원을 판별해 새 주문에도 reserveDate를 그대로 승계한다. 단, 새 주문의 status는 예약 여부와 무관하게 항상 일반 주문과 동일하게 'pending'으로 생성된다 — 예약주문 전용 status는 존재하지 않으며, 처리 흐름(대기중→주문접수→배송완료) 자체가 일반 주문과 완전히 동일하다. reserveDate는 renderHistory()의 서버 동기화 단계에서 로컬 캐시에도 반영되어, SSE 재렌더 이후에도 판별이 깨지지 않는다.

8.8 예약 이벤트 날짜 범위·중복 신청 방지

  • 날짜 범위: _reserveSel['EVENT']가 선택된 상태로 openReservePopup()이 호출되면 _reserveDateMin=이벤트 deadline, _reserveDateMax=deadline+7일로 재계산된다. 일반 예약주문(오늘+1~7일)과 달리 이벤트의 예약 가능일은 기한일 이후 1주일로 별도 규칙을 따른다.
  • 중복 방지: POST /api/orders에서 items에 menuId==='EVENT' 항목이 있으면, 같은 phone+같은 reserve_date로 status!='cancelled'인 기존 이벤트 주문이 있는지 조회한다(항목의 menuId를 JS에서 JSON 파싱 후 비교). 발견되면 INSERT 이전에 409로 거부 — 같은 고객이 같은 이벤트를 같은 날짜로 중복 신청하는 것을 막는다. 다른 날짜거나 일반 메뉴 예약은 이 검사 대상이 아니다.

9. 실시간 동기화 (SSE)

클라이언트는 window.onload에서 _startSSE()로 EventSource(API_URL+'/api/events') 연결. 서버는 변경 API마다 broadcast(type, payload)로 모든 연결에 이벤트 전송. 클라이언트는 수신 시 _debouncedRenderHistory()(500ms 디바운스)로 주문내역을 갱신한다.

이벤트 type발행 시점
order_new주문 생성
order_status상태 변경
order_request / order_memo / order_reply / order_ack / order_delete각 항목 변경
  • 서버: 25초 heartbeat(:\n\n)로 Railway 타임아웃 방어, X-Accel-Buffering:no 설정.
  • 클라이언트: onerror 시 close 후 5초 뒤 자동 재연결.
  • 입력 중(textarea/input focus)이면 재렌더를 blur 시점까지 지연하여 입력 방해 방지.

10.2 결제

온라인 PG 미사용. 계좌이체 수동 결제 — 결제화면에서 계좌 안내 후 고객이 직접 이체, 관리자가 입금 확인 시 상태를 confirmed로 변경.

11. 데이터 정합성 · 마이그레이션

서버 기동 시 initDB()는 CREATE TABLE IF NOT EXISTS로 테이블을 생성한다. 과거에는 settings 테이블의 플래그 키로 스키마 변경·데이터 보정용 1회성 마이그레이션들(menu_id 정규화, icon 컬럼 도입, img_url 보강, 중복 메뉴 병합, customers_master 컬럼 정리 등)을 실행했으나, 운영 DB에 모두 반영 완료되어 더 이상 필요 없으므로 코드에서 전부 제거했다. 이후 스키마 변경이 필요하면 CREATE TABLE 정의 자체에 반영하거나, 필요 시점에 한해 별도 스크립트로 처리한다.

13.2 [시퀀스] 재주문 — 취소 후 신규 생성과 재고부족 롤백

reorder()는 "원본 주문 취소 → 신규 주문 생성" 순서로 처리한다. 신규 생성이 재고부족으로 실패하면 원본 상태를 복원하고 품절 모달을 표시한다(보상 트랜잭션).

그림 13-2. 재주문 시퀀스 — 성공/재고부족 분기와 보상 처리

관리자가 주문 상태를 바꾸면, 서버가 모든 SSE 연결로 이벤트를 푸시하고 각 고객 클라이언트는 디바운스 후 주문내역을 재렌더한다.

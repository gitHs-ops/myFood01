A-2. 카카오 발송 텍스트 생성 → 파싱 역등록

업주는 카카오 발송 탭에서 생성된 텍스트를 복사해 카카오 비즈니스 채널로 1000명에게 보냅니다. 반대로 카톡 텍스트를 붙여넣어 일일 메뉴를 만드는 기능도 있습니다 — parseKakaoToMenu() menu-manager.html:1608.

종결 P1-1 카톡 파싱 재등록 — 업무 지침으로 처리(코드 수정 안 함)
무엇이었나
menu-manager.html:1650의 menus=parsed.map(...)가 그날 목록을 통째로 갈아엎으면서 재고를 설정 기본값으로 되돌립니다. 파싱된 메뉴에는 baseStock이 없어 P0-1의 재고 보존이 적용되지 않습니다(서버가 "새로 추가한 메뉴"로 판단).
왜 고치지 않나
업주 판단 — ①주문이 들어온 뒤 파싱을 다시 누르는 일은 사전 업무 지침으로 막습니다. ②설령 눌러도 재고는 무시해도 됩니다. 반찬가게는 계속 만들어 내므로 재고가 고정 수량이 아니고, 업주가 수시로 갱신하는 값입니다. 초기화되더라도 곧 업주가 실물 기준으로 다시 맞춥니다.
남는 것
재고와 무관한 부작용 하나는 코드로 고쳤습니다 — 파싱된 메뉴는 menuId 없이 이름으로 마스터를 찾는데, 마스터 고유키는 (이름 + 카테고리)입니다. 실제로 동명 마스터가 9건 있어(부대찌개·동태탕·낙지연포탕 등 메인/밀키트 짝) 엉뚱한 쪽에 연결되면 카테고리·사진이 뒤바뀔 수 있었습니다. 조회 조건에 카테고리를 더해 해결했습니다.

해결 P1-2 서버가 결제 금액을 검산하지 않던 문제
무엇이었나
POST /api/orders가 화면이 보낸 order.total을 그대로 저장했습니다. 주문 수정 API는 서버가 다시 계산하는데(주석에도 "클라이언트 값을 신뢰하지 않고"라고 적혀 있음) 생성 경로만 빠져 있었습니다. 총액뿐 아니라 items 안의 price도 화면 값이라, 합계만 재계산해서는 부족했습니다.
어떻게 고쳤나
단가를 DB에서 다시 읽어 합계를 계산합니다. 조회 순서는 그날 노출 메뉴(menu_id) → 마스터(menu_id) → 그날 노출 메뉴(이름)이며, 예약주문은 오늘 목록에 없어도 마스터 단가로 검산됩니다. 예약 이벤트처럼 어디에도 없는 항목만 화면 값을 그대로 둡니다. 배송비(매장픽업 아니고 2만원 이상 → 1천원)도 서버가 판정합니다.
화면 값과 다르면
서버 값으로 저장하되 기록을 남깁니다(console.warn, Railway 로그에서 확인). 조용히 덮기만 하면 화면 계산 버그를 영영 못 찾고, 주문을 거부하면 정상 고객이 막히기 때문입니다. 알림 문구에도 검산된 금액이 쓰입니다.
검증

남긴 선택지
2만원 미만 배달을 서버가 거부하도록 막지는 않았습니다. 화면이 이미 막고 있어 정상 고객은 여기 걸리지 않지만, 재오픈 직후에 주문이 거부되는 쪽이 더 위험하다고 판단했습니다. 금액은 정확히 저장되므로 업주가 접수 단계에서 판단할 수 있습니다.
P0-6 알림톡·SMS가 하나도 나가지 않고 있다 (2026-08-08 발견)
확인된 사실
운영 DB의 settings 테이블에 gasUrl 키가 아예 없습니다. _getNotifySettings()(server.js:70-77)가 이 값을 읽어오는데, 없으면 _notifyOrder·_notifyStatus·관리자 답변 알림이 모두 if (!url) return;에서 즉시 빠져나갑니다(:99, :121, :766).
왜 이렇게 됐나
gasUrl을 저장하는 코드가 어디에도 없습니다. 관리자 설정 화면의 syncSettingsToSheet()는 stock·smsEnabled·alimtalkEnabled·phone·email·deliveryPhone·banks만 보내고, GAS 주소를 입력하는 칸 자체가 화면에 없습니다. 과거 프런트에 하드코딩돼 있던 것을 서버 DB로 옮기는 과정에서 값을 옮겨 심는 단계가 빠진 것으로 보입니다. (설계서에는 saveSendSettings()가 gasUrl을 저장한다고 적혀 있으나 실제 함수는 발송 토글 두 개만 저장합니다 — 문서가 코드와 다릅니다.)
키 이름도 어긋나 있다
관리자 화면은 업주 번호를 phone으로 저장하는데 서버는 adminPhone을 찾습니다(server.js:72,108). 따라서 gasUrl을 채워 넣어도 업주 새 주문 SMS는 여전히 안 나갑니다. 두 가지를 함께 고쳐야 합니다.
영향
고객은 주문 접수·확정·배송완료·취소 알림톡을 한 통도 못 받습니다. 업주는 새 주문 SMS를 못 받으므로, 새 주문을 아는 경로가 관리자 화면을 열어두는 것 하나뿐입니다. 화면을 닫아둔 시간대의 주문은 그대로 묻힙니다. 고객 100명으로 늘리려는 계획에서 가장 먼저 터질 지점입니다.
수정
① GAS 배포 URL을 settings.gasUrl에 넣습니다(관리자 화면에 입력칸을 추가하거나, 우선 서버에서 1회 직접 저장). ② 서버가 읽는 키를 adminPhone에서 phone으로 맞추거나, 화면이 adminPhone으로도 함께 저장하게 합니다. ③ 그다음에 아래 P1-3(실패를 기록·통보)을 얹습니다.
P1-3 알림톡·SMS가 실패해도 아무도 모른다
어디서
server.js:82 — fetch(...).catch(() => {}). 발송 전체가 "보내고 잊는" 방식이고 실패를 기록도, 재시도도, 통보도 하지 않습니다. _notifyOrder/_notifyStatus의 바깥 try...catch(e){}(:113, :149)도 비어 있습니다.
왜 중요한가
바로 이것 때문에 P0-6이 지금까지 드러나지 않았습니다. 알림이 한 통도 안 나가는 상태였는데 어디에도 오류가 남지 않아 아무도 몰랐습니다. 앞으로도 솔라피 잔액 소진, 템플릿 승인 만료, GAS 일일 한도 초과가 모두 같은 방식으로 조용히 일어납니다.
수정
최소 조치: 실패 시 console.error로라도 남겨 Railway 로그에서 추적 가능하게 합니다. 권장: settings에 lastNotifyError 키를 저장하고 관리자 화면 상단에 "최근 알림 발송 실패" 배지를 띄웁니다.

4. 시나리오 C — 동시 주문 경합

왜 P0인가
업주가 정의한 접수완료의 의미는 "입금을 눈으로 확인했다"입니다. 즉 이 버튼은 돈과 직결됩니다. 한 번의 오터치로 미입금 주문이 조리·배송 대상으로 넘어가고, 그러면 지난 계좌 사고와 같은 종류의 돈 사고가 됩니다. 주문 목록에서 버튼들이 좁게 붙어 있어 스마트폰 조작 시 오터치 확률이 낮지 않습니다. 알림 발송이 정상화되면 고객에게 접수 알림톡도 나가는데, 이미 발송된 알림은 취소할 수 없습니다.
수정
다른 함수들과 동일하게 showConfirm('입금을 확인하셨나요? …', ...)로 감쌉니다. 이미 있는 공용 모달을 쓰므로 3줄입니다. 문구에 "입금 확인"을 명시하는 것이 이 사고의 핵심 방어입니다.
P1-4 입금 여부를 기록할 자리가 시스템에 없다
현황
주문 상태는 pending / confirmed / delivered / cancelled 넷뿐입니다(server.js:959). 입금액·입금자명·입금시각을 남길 컬럼이 없습니다. "입금 확인"은 오직 업주의 머릿속과 은행 앱에만 존재합니다.
어떻게 터지나
①입금자명이 주문자와 다를 때(가족 명의) 대조 실패 → 확인 지연·누락. ②부분 입금·초과 입금 시 기록할 곳이 없음. ③업주가 여러 건을 몰아 확인하다 한 건을 건너뛰면 그 주문은 영원히 대기중으로 남고 아무도 알아채지 못합니다. ④마감 시점에 "오늘 미입금 몇 건"을 볼 방법이 없습니다.
수정
재오픈 전(최소): 관리자 주문 화면에 "대기중 N건 / 미입금 합계 N천원" 요약을 띄웁니다. 이미 menu-manager.html:2390에서 상태별 건수를 세고 있으므로 표시만 추가하면 됩니다. 마감 전 대기중 0건을 확인하는 습관이 곧 미입금 방지책입니다.
오픈 후: orders에 paid_at DATETIME, payer_name VARCHAR(50) 추가 + 접수완료 시 입금자명 입력란(비워도 진행 가능).

6. 시나리오 E — 배송완료·마감

E-1. 배송완료 처리

menu-manager.html:2553에 배송완료 차단 조건이 있습니다 — 예약일이 안 맞거나(reserveMismatch) 오늘이 아닌 날짜(notToday)면 버튼을 막습니다. 오늘 날짜 주문을 실수로 다른 날에서 처리하는 것을 방지하는 좋은 장치입니다.

P2-2 마감 개념이 시스템에 없다

결과

수정

8. 시나리오 G — 카톡 주문 수작업 병행

업주는 기존 고객 1000명에게 닿는 유일한 통로가 카카오 비즈니스 채널이므로, 웹 주문과 카톡 답장 주문이 당분간 함께 갑니다. 카톡 주문은 업주가 시스템 밖에서 수작업으로 처리합니다.
G-1. 병행 운영에서 생기는 구조적 어긋남
P1-6 관리자 화면에 주문을 직접 입력하는 기능이 없다
확인 결과
menu-manager.html 전체를 훑었으나 업주가 주문을 수기로 등록하는 화면·함수가 없습니다. 주문 생성 경로는 고객 화면의 saveOrder()와 submitReserveOrder() 둘뿐입니다. (참고: "카카오 파싱"은 메뉴를 등록하는 기능이지 주문 등록이 아닙니다.)
그래서 무슨 일이 생기나
카톡으로 받은 주문은 시스템에 들어오지 않습니다. 따라서 ①재고가 안 맞습니다 — 카톡 주문 10개가 팔려도 시스템 재고는 그대로라 웹 고객에게 초과 판매됩니다. 이것이 병행 운영의 가장 큰 실무 위험입니다. ②그날 총 매출·총 주문 건수를 한 화면에서 볼 수 없습니다. ③카톡 주문 고객에게는 알림톡이 안 갑니다.
재오픈 전 대응(코드 수정 없이)
업주가 카톡 주문을 받을 때마다 관리자 화면에서 해당 메뉴의 재고를 그만큼 직접 줄이는 운영 규칙을 정합니다. 재고 수정 기능은 이미 있습니다. 이것만 지켜도 초과 판매는 막힙니다.
오픈 후 과제
관리자 화면에 수기 주문 등록을 추가합니다. 서버는 손댈 필요가 없습니다 — POST /api/orders를 그대로 쓰되 deviceId를 비우고 이름·전화·메뉴·수량만 넣으면 재고 차감·알림톡이 전부 기존 흐름을 탑니다. 화면 하나만 만들면 됩니다.
알아둘 점 — 수기 등록을 만들더라도 그 주문에는 기기ID가 없으므로 그 고객의 휴대폰 주문내역에는 표시되지 않습니다. 전화번호로 조회하는 경로는 서버에 이미 있으니(GET /api/orders?phone=, server.js:440), 고객 화면이 기기ID뿐 아니라 전화번호로도 조회하게 하면 해결됩니다. 순서상 P2-4(주문내역을 서버 기준으로 전환)와 함께 처리하는 것이 자연스럽습니다.

9. 시나리오 H — 예약주문

H-1. 흐름과 재고 처리

고객이 submitReserveOrder()(onban01.html)로 내일~7일 이내 날짜를 지정해 주문합니다. 주문 번호는 RSV로 시작하고 reserve_date가 채워집니다.

예약주문은 재고를 전혀 건드리지 않습니다. 생성 시 차감 안 함(server.js:502 if(!isReserve)), 접수완료·취소 시에도 모든 재고 연산을 건너뜁니다(server.js:583 isReserveOrder). 이는 의도된 설계입니다 — 예약일의 메뉴가 아직 등록되지 않았을 수 있기 때문입니다.

P2-3 예약주문은 그 날짜의 재고에 반영되지 않는다
결과
8월 12일자 예약주문 5건이 있어도, 8월 12일 아침에 메뉴를 등록할 때 재고에서 5개가 빠져 있지 않습니다. 업주가 예약 목록을 직접 보고 수동으로 빼야 합니다. 관리자 화면에 "예약된 메뉴" 탭이 있어 조회는 가능합니다(menu-manager.html loadReservedOrders()).
대응
재오픈 전에는 운영 규칙으로 충분합니다 — 아침 메뉴 등록 시 "예약된 메뉴" 탭을 먼저 확인하고 그만큼 재고를 늘려 잡습니다. 코드 수정은 오픈 후에.

양호 같은 전화번호로 같은 날짜에 같은 예약 이벤트를 중복 신청하는 것은 서버가 막고 있습니다(server.js:487-497).

  • 고객 알림톡은 배송완료 때만 보냅니다. 주문 시점에 카톡이 가면 고객이 그 대화방에서 답장해 옛 주문 방식으로 되돌아가기 때문입니다(업주 판단). settings.notifyEvents 배열로 시점을 제어하며 현재 값은 ["delivered"]입니다. 여기에 confirmed·cancelled·reply·order를 넣으면 그 시점도 함께 발송됩니다.
  • 업주 SMS와 배송업체 SMS는 쓰지 않습니다(smsEnabled=false). 업주는 관리자 화면의 변화를 보고 대응하는 방식을 택했습니다.
  • 그래서 관리자 화면이 새 주문을 아는 유일한 경로가 됐고, 아래 두 가지를 새로 넣었습니다.
보완 알림 문자를 안 쓰는 대신 넣은 장치 두 가지
새 주문 소리·진동·탭 제목 알림
실시간 신호 중 order_new가 왔을 때만 '딩-동' 소리를 두 번 울리고, 지원 기기에서는 진동하며, 브라우저 탭 제목이 🔔 새 주문 N건!으로 깜빡입니다. 소리는 오디오 파일 없이 코드로 만들어 정적 호스팅에서도 그대로 동작합니다. 주의: 브라우저는 사용자가 화면을 한 번 건드리기 전에는 소리를 막으므로, 관리자 화면에 들어와 아무것도 누르지 않으면 첫 알림이 안 울릴 수 있습니다.
묻힌 주문 경고 + 미입금 합계
소리는 화면을 열어둔 동안만 울립니다. 브라우저를 닫아둔 사이의 주문은 여전히 놓칠 수 있으므로, 지난 날짜에 대기중으로 남은 주문을 GET /api/orders/pending-summary로 집계해 주문 화면 상단에 "처리 안 된 지난 주문 N건" 경고를 띄웁니다. 해당 날짜로 바로 이동하는 버튼도 함께 나옵니다. 대기중 통계에는 미입금 합계 금액을 표시해, 마감 전에 이 숫자만 확인하면 됩니다. (P1-4·P2-2 해소)
P0-4 관리자 비밀번호가 공개 소스에 그대로 적혀 있다
어디서
menu-manager.html:12의 ADMIN_PW, menu-manager.html:2858의 ADMIN_API_TOKEN, index.html:9의 ADMIN_PW — 세 곳 모두 같은 값이 평문으로 박혀 있습니다.
왜 심각한가
프런트는 GitHub Pages로 배포되고 저장소가 공개이므로, 브라우저에서 소스 보기만 해도 비밀번호가 보입니다. 이 토큰 하나로 관리자 전용 API 전부(메뉴 전체 삭제, 주문 삭제, 설정·계좌 변경)를 호출할 수 있습니다. 계좌 정보를 바꿔치기하는 것도 가능합니다 — 지난 사고보다 더 큰 형태의 같은 사고입니다.
추가로
onban_admin_auth 플래그가 '1' 고정값이라 비밀번호를 바꿔도 이미 접속했던 기기는 계속 통과합니다(menu-manager.html:13).
재오픈 전 최소 조치
①비밀번호를 새 값으로 변경 ②플래그를 비밀번호에 연동해 옛 기기 자동 차단(var AUTH_VAL='ok_'+ADMIN_PW 방식, 3줄) ③Railway 환경변수 ADMIN_TOKEN도 같이 변경. 근본 해결은 아니지만 유출된 값은 무효화됩니다.
오픈 후 근본 수정
POST /api/admin/login을 만들어 서버가 비밀번호를 검증하고 토큰을 내려주는 방식으로 전환, HTML에서 비밀번호·토큰 하드코딩을 완전히 제거합니다. 자세한 내용은 localStorage_잔존값_제거_방안.md §2 참고.
P0-5 설정 조회 API가 인증 없이 모든 값을 내준다
어디서
server.js:875 — GET /api/settings에 requireAdmin이 없고, settings 테이블의 모든 키를 통째로 반환합니다. 저장 쪽(server.js:887)에는 인증이 걸려 있는데 조회만 열려 있습니다.
무엇이 새는가
gasUrl(문자 발송 프록시 주소), adminPhone(업주 휴대폰), deliveryPhone(배송업체 연락처), banks(계좌 전체). 그리고 그 gasUrl은 인증이 없어(sms_proxy4onban.gs), 주소만 알면 누구나 임의의 번호로 문자를 보낼 수 있습니다 — 요금은 가게가 냅니다.
왜 인증을 못 거나
고객 화면이 계좌를 표시하려고 이 API를 쓰기 때문입니다(onban01.html:1757). 지난 계좌 사고를 고치면서 만든 경로라 없앨 수 없습니다.
수정 방향
인증을 걸지 말고 내주는 값을 가립니다. 관리자 토큰이 없으면 banks·카테고리 같은 고객에게 필요한 키만 반환하고 gasUrl·adminPhone·deliveryPhone은 제외합니다. 화이트리스트 방식 10줄이면 되고 고객 화면은 그대로 동작합니다.

5번(P0-1)을 마지막에 두는 이유 — 메뉴 저장은 매일 아침 반드시 쓰는 기능이라, 여기서 실수하면 재오픈 당일 아침에 메뉴 등록 자체가 막힙니다. 앞의 네 건을 먼저 올려 안정시킨 뒤, 실제 날짜로 등록→주문→재저장을 직접 돌려 재고가 유지되는지 확인하고 배포하십시오.

배포 후 검증 (본인이 직접)

  • 고객 화면에서 주문 1건 넣고 → 관리자 화면에서 실시간으로 뜨는지, 업주 휴대폰에 문자가 오는지
  • 같은 상태에서 관리자 화면 메뉴를 하나 고쳐 저장 → 주문으로 빠진 재고가 유지되는지 (P0-1 검증, 가장 중요)
  • 주문 확정 버튼 빠르게 두 번 클릭 → 주문이 1건만 생기는지 (P0-2)
  • 접수완료 클릭 → 확인창이 뜨고 문구에 "입금"이 들어 있는지 (P0-3)
  • 비밀번호 바꾼 뒤 기존에 로그인돼 있던 기기에서 다시 물어보는지 (P0-4)
  • 브라우저 주소창에 .../api/settings를 직접 열어 문자 발송 주소와 연락처가 안 보이는지 (P0-5)
  • 계좌를 바꿔보고 다른 기기(옛날에 접속했던 폰)에서 새 계좌가 보이는지 — 지난 사고 재발 확인

배포 운영 — 알아둘 것

Railway는 저장소 전체를 감시해서, HTML만 고쳐 올려도 서버를 통째로 재시작합니다. 그 1~2분 동안 API가 JSON 대신 오류 HTML을 돌려주고, 저장·삭제·상태변경이 전부 같은 경로를 타므로 한꺼번에 고장난 것처럼 보입니다. 실제로 2026-08-08 작업 중 이 증상을 겪었고, DB나 서버 문제로 오인하기 쉽습니다.
  • 해결(적용 완료): Railway 서비스 Settings → Build → Watch Paths에 /server/** 지정. 이제 서버 코드가 바뀔 때만 재배포되고, HTML만 고친 push는 서버를 건드리지 않습니다.
  • 화면 쪽 보완: 재배포 중 응답을 못 읽으면 Unexpected token '<' 대신 "서버가 잠시 응답하지 않아요. 30초쯤 뒤 다시 시도해주세요"가 뜹니다. 통신을 감싸는 한 곳에서 처리합니다.
  • 배포 반영 확인: /health가 build 표식을 돌려줍니다. 서버 코드를 고칠 때 이 값을 함께 바꾸면 재배포가 끝났는지 바로 알 수 있습니다.
  • 화면 캐시: GitHub Pages는 배포 후 최대 10분간 옛 파일을 내보냅니다(max-age=600). Railway 정적 서빙은 즉시 반영되므로, 수정이 잦은 날 관리자 화면은 Railway 주소로 여는 편이 낫습니다.

업주에게 전달할 운영 규칙

  • 접수완료 버튼은 은행 입금을 확인한 뒤에만 누른다. 누르는 순간 배송업체에 배송 요청 문자가 나가며 취소할 수 없다.
  • 카톡으로 받은 주문은 관리자 화면에서 그 메뉴의 재고를 그만큼 직접 줄인다. 안 그러면 웹 고객에게 없는 물건을 팔게 된다.
  • 아침 메뉴 등록 전에 "예약된 메뉴" 탭을 먼저 확인하고 그 수량만큼 재고를 넉넉히 잡는다.
  • 메뉴 화면을 장시간 열어두지 않는다. 특히 주문이 몰리는 시간에 화면을 열어둔 채 저장하지 않는다.
  • 재고를 직접 수정할 때는 주문이 뜸한 시간에 한다.
  • 마감 전 "대기중" 주문이 남아 있는지 반드시 확인한다. 대기중 = 아직 입금 확인이 안 된 주문이다.
  • 계좌를 바꿨으면 관리자 화면 설정에서 반드시 저장하고, 다른 폰으로 주문 화면에 들어가 새 계좌가 보이는지 눈으로 확인한다.

이 점검의 한계 — 반드시 알아둘 것

이 점검은 코드와 설계서를 읽어서 한 도상 점검입니다. 실제 화면을 띄워 눌러본 것이 아니고, 업주 인터뷰나 모의 주문 리허설도 하지 않았습니다. 따라서 여기서 찾지 못한 문제가 있을 수 있습니다 — 특히 업주가 실제로 화면을 어떻게 조작하는지, 어떤 순서로 버튼을 누르는지에서 오는 문제는 코드만 봐서는 보이지 않습니다.

지난 계좌번호 사고도 정확히 그 지점에서 났습니다. 재오픈 첫날은 업주 곁에서 또는 통화 가능한 상태로 지켜보시길 권합니다. 수정을 다 하더라도 그것이 마지막 방어선입니다.

3. 고치는 과정에서 새로 드러난 것 13건

최초 점검은 코드를 읽어서 한 도상 점검이었고, 실제로 고치고 돌려보는 과정에서 읽기만 해서는 안 보이던 것들이 나왔습니다. 대부분 재오픈 후 실운영에서 터졌을 종류입니다.

#발견상태왜 안 보였나
1알림톡·문자가 한 통도 안 나가고 있었음 — settings.gasUrl이 아예 없음해결실패가 기록되지 않아 아무도 몰랐음. 저장하는 코드 자체가 프로젝트에 없었음
2솔라피 API 키의 IP 제한으로 알림톡 전부 거절해결외부 계정 설정. 발송 기록을 만들고 나서야 응답이 보였음
3CORS 허용 목록에 서버 자기 주소가 빠져 Railway 주소로 열면 저장·삭제가 전부 실패해결읽기는 되고 쓰기만 막혀 서버·DB 장애처럼 보였음. curl은 Origin을 안 보내 재현 불가
4comma() 미정의 → 대기중 주문이 있으면 주문 화면 전체가 오류해결다른 HTML에만 있는 함수. 문법 검사로는 안 잡힘. 대기중 주문이 생겨야 터짐
5업주 번호를 phone으로 저장하는데 서버는 adminPhone을 조회해결키 이름 불일치. 발송 주소를 채워도 업주 문자는 영영 안 갔을 것
6주문 수정이 자동 저장이라 수량을 누를 때마다 변경 문자 발송해결저장 버튼이 사실상 장식이었음. 변경 통보를 붙이고 나서야 드러남
7배송방법 변경도 별도 경로로 즉시 발송해결수량과 다른 경로를 타고 있었음
8그 경로를 옛 형식 정리 코드도 사용 — 고객이 화면만 열어도 문자가 나갈 뻔해결사용자 동작이 아닌 자동 실행 경로
9발송 설정 토글이 저장 버튼 없이는 반영 안 되는데, 실패해도 "저장되었습니다"해결토글은 즉시 적용되는 것처럼 보임. 결과를 확인하지 않았음
10일일 메뉴를 전부 지우면 서버가 404를 주는데 화면 갱신을 건너뜀해결정상 응답이 아니면 아무것도 안 하는 구조. 삭제했는데 안 된 것처럼 보였음
11saveToday()가 같은 내용을 서버에 두 번 저장해결절대값 저장일 땐 무해. 재고 보존(변경분 방식)으로 바꾸면서 문제가 됨
12마스터 메뉴를 이름만으로 찾음 — 동명 9건(메인/밀키트 짝)이 실재해결고유키는 (이름+카테고리). 카테고리·사진이 뒤바뀔 수 있었음
13histSaveMemo가 선택 요소를 못 찾으면 배송방법을 빈 값으로 지움해결검증 테스트를 돌리다 발견. 배송비 계산까지 틀어짐
여기서 얻은 교훈 하나 — 문법 검사만으로는 부족합니다. 4번(comma())과 13번은 문법이 통과하는데도 실제로는 깨지는 코드였고, 둘 다 실제 데이터를 넣어 실행해 보고서야 잡혔습니다. 이후 수정은 모두 해당 로직을 잘라내 실행 검증했습니다.

4. 남은 위험 4건

1 카톡 주문이 재고에 반영되지 않는다 (P1-6)
현황
관리자 화면에 주문을 직접 입력하는 기능이 없습니다. 카톡으로 받은 주문은 시스템 밖에 있으므로 재고가 줄지 않고, 웹 고객에게 초과 판매됩니다. 병행 운영이 계속되는 한 남는 위험입니다.
지금 할 것
카톡 주문을 받으면 그 메뉴의 재고를 관리자 화면에서 직접 줄인다 — 운영 규칙으로 막습니다. 재고 조정 기능은 이미 있습니다.
오픈 후
수기 주문 등록 화면을 만듭니다. 서버는 손댈 필요가 없습니다 — POST /api/orders를 그대로 쓰되 기기ID를 비우면 재고 차감·기록이 전부 기존 흐름을 탑니다.
2 카테고리가 관리자 기기에만 있다 (P2-5)
현황
menu-manager.html:836 — 카테고리 원본이 브라우저 저장소에만 있습니다. 서버에 저장하는 코드가 없습니다.
영향
관리자 폰을 바꾸거나 브라우저 데이터를 지우면 카테고리 설정이 통째로 사라집니다. 고객 화면에도 전파되지 않아 하드코딩 기본색만 보입니다.
수정
서버는 이미 준비돼 있습니다 — categories가 공개 키 목록에 들어 있어 화면만 고치면 됩니다. 지난 계좌번호 사고와 같은 부류이므로 오픈 후 우선 처리를 권합니다.
3 예약주문이 그 날짜 재고에 반영되지 않는다 (P2-3)
현황
예약주문은 재고를 전혀 건드리지 않습니다(의도된 설계 — 예약일 메뉴가 아직 없을 수 있음).
지금 할 것
아침 메뉴 등록 전에 "예약된 메뉴" 탭을 먼저 확인하고 그 수량만큼 재고를 넉넉히 잡습니다.
4 비밀번호가 공개 소스에 평문 (P0-4 잔여)
현황

서버가 비밀번호를 검증하고 토큰을 내려주는 방식으로 바꿔야 근본 해결입니다. 오픈 후 과제.

5. 재오픈 체크리스트

아직 확인하지 못한 것 — 직접 해보셔야 합니다

  • 재고 보존 — 관리자 화면을 열어둔 채 다른 기기로 주문을 넣고, 메뉴를 하나 고쳐 저장했을 때 주문으로 빠진 재고가 유지되는지. 이번 작업에서 가장 중요하고 매일 아침 쓰는 기능인데 실제 확인이 남아 있습니다.
  • 배송완료 알림톡 — 시험 주문을 배송완료로 바꿔 고객 폰에 도착하는지 (서버 응답은 success:true 확인됨)
  • 업주 새 주문 문자 — 주문을 하나 넣어 업주 휴대폰에 오는지
  • 주문 변경 문자 — 고객 화면에서 수량을 바꾸고 저장 → 확인창 → 네 → 문자 한 통만 오는지
  • 새 주문 소리 — 관리자 화면에 들어가 아무 곳이나 한 번 누른 뒤 다른 기기로 주문. 브라우저는 화면을 건드리기 전에는 소리를 막습니다

업주에게 전달할 운영 규칙

  • 접수완료는 은행 입금을 확인한 뒤에만 누른다. 되돌릴 수 없다.
  • 카톡으로 받은 주문은 관리자 화면에서 그 메뉴의 재고를 직접 줄인다. 안 그러면 없는 물건을 팔게 된다.
  • 아침 메뉴 등록 전에 "예약된 메뉴" 탭을 먼저 확인하고 그 수량만큼 재고를 넉넉히 잡는다.
  • 주문이 들어온 뒤에는 카톡 파싱 등록을 다시 누르지 않는다.
  • 마감 전 "대기중" 건수와 "처리 안 된 지난 주문" 경고를 확인한다. 대기중 = 아직 입금 확인이 안 된 주문이다.
  • 계좌를 바꿨으면 설정에서 저장하고, 다른 폰으로 주문 화면에 들어가 새 계좌가 보이는지 눈으로 확인한다.

  • 알림이 안 나가면 기록부터 봅니다. settings.lastNotify에 마지막 발송 결과와 실패 사유가, lastNotifyTrigger에 어떤 주문의 어떤 상태에서 시도했는지가 남습니다.
  • 배포 반영은 /health로 확인. build 값이 바뀌면 새 서버가 뜬 것입니다. 현재 order-log-2.
  • 화면에 "서버 응답을 읽지 못했어요 (숫자 경로)"가 뜨면 그 숫자와 경로를 알려주면 원인을 바로 짚을 수 있습니다.
